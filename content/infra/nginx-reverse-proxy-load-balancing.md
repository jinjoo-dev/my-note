서비스 구조도를 살펴보다가, 클라이언트와 API 서버 사이에 있는 **Nginx**가 눈에 들어왔어요.

```text
          클라이언트
              │
              ▼
            Nginx
              │
       ┌──────┴──────┐
       ▼             ▼
     서버 A         서버 B
```

클라이언트가 API 서버를 호출하는 건 익숙한데, 중간에 Nginx를 두는 이유는 무엇일까요? 그리고 Nginx 뒤로 연결된 서버들은 어떤 기준으로 요청을 전달받는 걸까요?

이 궁금증을 계기로 Nginx의 역할을 찾아보면서, **리버스 프록시, 요청 라우팅, 로드 밸런싱**의 차이를 정리해 봤어요.

> 이 글의 구성도, 주소, 서비스 이름은 개념 설명을 위한 가상 예시예요. 특정 조직의 실제 운영 구성을 나타내지 않아요.

## 1. Nginx란 무엇일까?

**Nginx**(엔진엑스)는 웹 서버 소프트웨어예요. 정적 파일을 제공하는 웹 서버로 사용할 수 있고, 다른 서버에 요청을 전달하는 리버스 프록시나 여러 서버에 요청을 분산하는 로드 밸런서로도 사용할 수 있어요.

각 역할을 간단히 구분하면 다음과 같아요.

| 역할 | 설명 |
|---|---|
| 웹 서버 | HTML, CSS, JavaScript, 이미지 같은 정적 파일을 제공해요. |
| 리버스 프록시 | 클라이언트의 요청을 받아 다른 서버에 전달해요. |
| 로드 밸런서 | 여러 서버에 요청을 나눠 전달해요. |

이 역할들은 서로 배타적이지 않아요. 하나의 Nginx가 정적 파일을 제공하면서 API 요청을 백엔드로 전달하고, 여러 백엔드 인스턴스에 요청을 분산할 수도 있어요.

먼저 요청을 다른 서버로 전달하는 **리버스 프록시**부터 살펴볼게요.

## 2. 리버스 프록시란?

프록시(Proxy)는 ‘대리인’이라는 뜻이에요. 네트워크에서는 요청과 응답을 중간에서 대신 전달하는 구성 요소를 말해요.

그중 **리버스 프록시는 서버 앞에서 클라이언트의 요청을 받아 백엔드 서버에 전달하는 역할**을 해요.

상품 목록을 조회하는 상황을 예로 들어볼게요.

```text
클라이언트
    │
    │ GET /api/products
    ▼
  Nginx
    │
    ▼
상품 API 서버
    │
    ▼
상품 목록 조회
```

이 구성에서 상품 목록을 조회하는 주체는 API 서버예요. Nginx는 요청을 전달하고, API 서버가 반환한 응답을 다시 클라이언트에 전달해요.

### 리버스 프록시가 없는 경우

```text
클라이언트 → API 서버
```

클라이언트가 API 서버에 직접 접근해요.

이 구성도 가능하지만, 클라이언트에 노출하는 접점과 실제 API 서버를 별도로 관리하기는 어려울 수 있어요.

### 리버스 프록시가 있는 경우

```text
클라이언트 → Nginx → API 서버
```

클라이언트는 공개된 서비스 주소로 요청하고, Nginx가 백엔드로 전달해요. 클라이언트는 실제 요청을 처리하는 백엔드의 IP나 포트를 알 필요가 없어요.

예를 들어 공개 주소는 그대로 유지하면서 Nginx가 전달하는 백엔드 주소만 바꿀 수 있어요.

다만 리버스 프록시가 없다고 해서 서버가 바뀔 때마다 반드시 클라이언트를 수정해야 하는 것은 아니에요. DNS 같은 다른 방법으로도 주소 변경을 추상화할 수 있어요. 리버스 프록시는 여기에 **HTTP 요청 단위의 전달 제어**를 더할 수 있다는 점이 중요해요.

### 왜 리버스 프록시를 사용할까?

**① 외부 접점과 내부 서버 구성을 분리할 수 있어요.**

외부 요청은 Nginx로 받고, 백엔드 서버는 내부 네트워크에서 운영하도록 구성할 수 있어요.

단, Nginx를 설치했다고 백엔드 접근이 자동으로 차단되는 것은 아니에요. 방화벽과 네트워크 접근 제한도 함께 설정해야 해요.

**② 공통 처리를 한곳에 모을 수 있어요.**

HTTPS 연결 처리, 요청 크기 제한, 접근 로그 기록 같은 기능을 프록시 계층에서 처리하도록 구성할 수 있어요.

**③ 요청에 따라 전달 대상을 바꿀 수 있어요.**

상품 요청은 상품 서비스로, 회원 요청은 회원 서비스로 전달할 수 있어요. 이 동작을 **요청 라우팅**이라고 해요.

## 3. 요청 라우팅: 어떤 서비스로 보낼까?

요청 라우팅은 **요청의 조건을 보고 전달할 서비스를 선택하는 것**이에요.

대표적으로 도메인이나 URL 경로를 기준으로 나눌 수 있어요. 여기서는 경로를 기준으로 살펴볼게요.

| 요청 경로 | 전달 대상 |
|---|---|
| `/api/products/` | 상품 서비스 |
| `/api/users/` | 회원 서비스 |

```text
클라이언트 → Nginx
               ├─ /api/products/ → 상품 서비스
               └─ /api/users/    → 회원 서비스
```

여기서 상품 서비스와 회원 서비스는 **서로 다른 기능**을 제공해요.

상품 조회 요청을 회원 서비스에 보내면 안 되기 때문에, Nginx는 요청 경로에 맞는 서비스를 선택해야 해요.

Nginx에서는 다음과 같이 표현할 수 있어요.

```nginx
server {
    listen 80;
    server_name api.example.com;

    location /api/products/ {
        proxy_pass http://product_backend;
    }

    location /api/users/ {
        proxy_pass http://user_backend;
    }
}
```

`location`은 요청 URI에 적용할 설정을 정하고, `proxy_pass`는 요청을 전달할 대상을 지정해요. 위 예시는 백엔드 그룹이 별도로 정의되어 있다고 가정한 일부 설정이에요.

중요한 점은 **뒤에 서버가 두 개 있다는 이유만으로 로드 밸런싱이라고 부르지는 않는다는 것**이에요.

이 예시는 서로 다른 서비스를 선택하는 **라우팅**이에요.

## 4. 로드 밸런싱: 같은 서비스의 어느 인스턴스로 보낼까?

이번에는 상품 서비스만 생각해 볼게요.

상품 API를 처리하는 애플리케이션을 하나가 아니라 두 개 실행했다면 어떨까요?

```text
클라이언트 → Nginx → 상품 서비스 그룹
                       ├─ 상품 API 인스턴스 A
                       └─ 상품 API 인스턴스 B
```

A와 B는 같은 상품 API를 제공해요. 따라서 Nginx가 요청을 두 인스턴스에 나눠 보내도록 구성할 수 있어요.

이처럼 **여러 인스턴스에 요청을 분산하는 것이 로드 밸런싱**이에요.

여기서 인스턴스는 실행 중인 애플리케이션 하나를 뜻해요. 반드시 물리 서버 한 대와 일대일로 대응하는 것은 아니에요.

### 왜 인스턴스를 여러 개 운영할까?

**① 처리 부하를 나누기 위해서예요.**

한 인스턴스에 요청이 몰리지 않도록 여러 인스턴스가 나눠 처리할 수 있어요.

다만 인스턴스를 두 개로 늘린다고 전체 처리량이 반드시 두 배가 되는 것은 아니에요. 공통으로 사용하는 DB나 외부 API가 병목일 수도 있기 때문이에요.

**② 일부 인스턴스의 장애에 대비하기 위해서예요.**

A가 요청을 처리할 수 없더라도 B가 정상이라면, B로 요청을 보내 서비스를 이어갈 수 있어요.

물론 인스턴스를 여러 개 띄우는 것만으로 충분하지는 않아요. 실패를 감지하고 전달 대상을 조정하는 동작, 타임아웃과 재시도 정책 등을 함께 고려해야 해요.

### Nginx의 대표적인 분산 방식

| 방식 | 선택 기준 |
|---|---|
| Round Robin | 서버 가중치를 고려해 요청을 순환 배분해요. |
| Least Connections | 활성 연결 수가 가장 적은 서버를 선택해요. |
| IP Hash | 클라이언트 IP를 기반으로 서버를 선택해요. |

기본 방식은 Round Robin이에요. 같은 가중치의 정상 서버 두 개라면 요청을 번갈아 배분하는 것으로 이해할 수 있어요. 다만 응답이 완료되는 순서까지 A → B → A → B로 보장한다는 뜻은 아니에요.

또한 Least Connections의 기준은 CPU 사용량이나 업무 처리량이 아니라 **활성 연결 수**라는 점도 구분하면 좋아요.

## 5. 라우팅과 로드 밸런싱은 함께 사용할 수 있어요

두 개념을 합치면 다음과 같은 구성이 돼요.

```text
클라이언트 → Nginx
               │
               ├─ /api/products/
               │       └─ 상품 서비스 그룹
               │              ├─ 인스턴스 A
               │              └─ 인스턴스 B
               │
               └─ /api/users/
                       └─ 회원 서비스 그룹
                              ├─ 인스턴스 C
                              └─ 인스턴스 D
```

개념적으로는 두 가지 선택이 일어나요.

1. **어떤 서비스로 보낼까?** → 요청 라우팅
2. **그 서비스의 어느 인스턴스로 보낼까?** → 로드 밸런싱

그리고 클라이언트의 요청을 대신 받아 백엔드에 전달하는 전체 역할은 **리버스 프록시**라고 할 수 있어요.

### 설정으로 살펴보기

```nginx
http {
    upstream product_backend {
        server 192.0.2.10:8080;
        server 192.0.2.11:8080;
    }

    upstream user_backend {
        server 192.0.2.20:8080;
        server 192.0.2.21:8080;
    }

    server {
        listen 80;
        server_name api.example.com;

        location /api/products/ {
            proxy_pass http://product_backend;
        }

        location /api/users/ {
            proxy_pass http://user_backend;
        }
    }
}
```

*주소는 문서 설명용 예시이며, 위 코드는 핵심 동작만 보여주는 최소 구성이에요. HTTPS와 접근 제어 등 운영에 필요한 설정은 생략했어요.*

각 설정의 역할은 다음과 같아요.

- `upstream`: 요청을 전달할 서버 그룹을 정의해요.
- `location`: 요청 URI에 따라 적용할 설정을 정해요.
- `proxy_pass`: 선택한 서버 또는 서버 그룹으로 요청을 전달해요.

이 예시에서는 `/api/products/` 요청을 상품 서비스 그룹으로 보내고, 그룹 안에서는 기본 Round Robin 방식으로 분산해요.

## 6. 오류가 나면 요청이 어디로 전달됐는지 살펴보기

API 요청에서 오류가 발생했다면, 클라이언트가 보낸 URL뿐 아니라 **요청이 어떤 경로를 거쳐 어디에서 처리됐는지**도 살펴볼 필요가 있어요.

프록시가 요청을 전달하는 과정에서 경로가 바뀔 수 있고, 여러 인스턴스 중 어느 곳에서 처리됐는지에 따라 결과가 달라질 수도 있기 때문이에요.

예를 들어 다음과 같은 상황을 구분해 볼 수 있어요.

| 오류 상황 | 확인할 내용 |
|---|---|
| 특정 경로에서만 오류가 발생해요. | 의도한 서비스로 전달됐는지, 전달된 경로가 올바른지 |
| 같은 요청이 성공하기도 하고 실패하기도 해요. | 특정 인스턴스에서만 오류가 발생하는지 |
| 여러 API가 동시에 실패해요. | Nginx나 공통으로 사용하는 백엔드·DB 등에 문제가 있는지 |

이런 증상은 **원인을 좁히기 위한 단서이지, 특정 원인을 확정하는 증거는 아니에요.**

브라우저 개발자 도구에서는 요청 URL과 응답 상태 등을 확인할 수 있지만, 프록시 이후에 어떤 백엔드 인스턴스가 처리했는지까지는 보통 알기 어려워요.

이때 Nginx와 애플리케이션 로그를 통해 **전달 대상, 응답 상태, 처리 시간**을 함께 살펴보면 문제 구간을 좁히는 데 도움이 돼요. 필요한 항목이 로그에 남도록 설정하고, 요청 ID를 함께 기록하면 같은 요청을 여러 계층에 걸쳐 추적하기도 쉬워져요.

즉, **“어떤 오류가 났는가”뿐 아니라 “그 요청이 어디로 전달됐고, 어디에서 실패했는가”를 확인하는 것**이 중요해요.

## 7. Nginx 자체에 장애가 발생하면?

백엔드 인스턴스가 모두 정상이더라도, 요청이 반드시 거쳐야 하는 Nginx가 한 대뿐이고 여기에 장애가 발생하면 요청이 백엔드에 도달하지 못할 수 있어요.

```text
클라이언트 → Nginx ❌ → 백엔드 인스턴스들
                           모두 정상
```

이처럼 **하나의 구성 요소에 장애가 발생했을 때 전체 서비스나 중요한 기능이 중단될 수 있는 단일 장애점**을 **SPOF**(Single Point of Failure)라고 해요.

이를 줄이기 위해 Nginx도 여러 인스턴스로 운영하고, 정상 인스턴스로 요청을 보내도록 구성할 수 있어요.

다만 **구조도에 Nginx 아이콘이 하나 있다고 해서 실제로 한 대만 운영한다고 판단해서는 안 돼요.** 하나의 아이콘이 여러 인스턴스로 구성된 계층을 나타낼 수도 있어요.

## 정리: 화살표보다 역할을 읽기

처음의 그림으로 돌아가 볼게요.

```text
클라이언트 → Nginx → 서버 A / 서버 B
```

이 그림만으로는 Nginx가 정확히 무엇을 하는지 단정할 수 없어요.

서버 A와 B가 다른 기능을 제공한다면 요청 라우팅일 수 있고, 같은 API를 제공하는 인스턴스라면 로드 밸런싱일 수 있어요. 하나의 Nginx에서 두 동작을 함께 수행할 수도 있어요.

핵심 개념을 정리하면 다음과 같아요.

| 개념 | 핵심 질문 |
|---|---|
| 리버스 프록시 | 클라이언트 요청을 누가 대신 받아 백엔드에 전달할까? |
| 요청 라우팅 | 이 요청을 어떤 서비스로 보낼까? |
| 로드 밸런싱 | 같은 서비스의 어느 인스턴스로 보낼까? |
| SPOF | 어느 한 곳이 고장 나면 서비스가 중단될까? |

앞으로 구조도를 볼 때는 기술 이름이나 서버 개수만 보기보다, 다음을 함께 확인해 보려고 해요.

- 각 서버는 같은 기능을 제공할까, 서로 다른 기능을 제공할까?
- 요청은 어떤 조건으로 분기될까?
- 분산 대상은 어떤 기준으로 선택될까?
- 일부 구성 요소에 장애가 나면 어떻게 될까?
- 그림에 생략된 계층이나 인스턴스는 없을까?

**구조도는 구성 요소를 보여주지만, 실제 동작을 이해하려면 각 요소의 역할과 설정을 함께 살펴봐야 해요.**
